Summarised prompt records

Summarised with the unit's permission rather than reproduced verbatim.

What we askedOutcome
Explain the unit's Docker setup and how to use VS Code with the container Explanation of bind mounts and container lifecycle. We set up the environment ourselves.
Should Task 1 replace worst-case allocation with an estimate? Advised against the common n/(ln n − 1) form (a lower bound, so it guarantees a reallocation) and proposed 1.2n/ln n. Confirmed on request that this is a memory optimisation with no effect on run time — we present it as such.
Compare our shared-array design against an alternative using per-thread buffers Trade-off analysis. Found a defect in the alternative (count not reset on allocation failure) and noted it used a different is_prime, which would contaminate the comparison. We kept our design.
Is contiguous block partitioning a good approach for Task 2? No — is_prime(k) costs ~√k, so the highest block finishes last. Proposed cyclic partitioning; we implemented and measured it: +18% to +23% at large n. Our largest optimisation.
Check our work against the specification and rubric Identified three unmet criteria: near-linear speed-up, "different OpenMP features", and experimental evidence for the Task 1 optimisations. The next three rows are our responses.
Tooling to collect the required measurements benchmark.sh / summarize.sh. We queried the three-repetition, best-of-N choice; the stated reason (parallel runs vary up to 22%, serial 4%) we confirmed in our own data.
How to evidence the Task 1 optimisations optbench.c, running three primality tests behind one identical harness. Measured 1,090× at n = 106; the odd-divisor skip alone gives a consistent 2.0×.
Is hard-coding schedule(static, 1) a problem? The code was fine; what was missing was evidence. Suggested a throwaway copy using schedule(runtime) to compare four schedules, and warned that shipping runtime would silently fall back to the slower default.
Why is our speed-up curve a staircase? Proposed a taskset pinning test. We measured a 13.3% difference between two and four physical cores, confirming the explanation.
Why 4.7× and not 8×? Is OpenMP really faster? SMT sharing the integer divider, the O(n) sequential compaction, thread-creation cost. The apparent 20% OpenMP advantage proved to be the partitioning difference, not the API — after fixing Task 2 the two are equal within noise.
Line-by-line explanation of task1.c and task2.c Pointers, malloc/realloc, sizeof, scanf, struct, the pthread API. We asked precisely because AI is not permitted in the Q&A and we must explain the code unaided.

Two instances where we did not simply accept the output: the AI predicted the contiguous version would cap near 2.8× when we measured 4.08×, and a single run appeared to show guided was 9.7% faster until five repetitions showed it was noise. Both are reported as measured.
